# 0G inference operations

The hosted runtime uses 0G Router when `ZG_MODE=router` and `INFERENCE_PROVIDER` is unset or `0g`. It requests `verified` provider routing and only accepts a result for execution when the Router reports it as verified. A Router verification flag is not an independently verified on-chain proof. The separate strategy-drafting compiler currently uses OpenRouter; it is not evidence that the hosted 0G agent works.

Use `pnpm 0g:providers` for a read-only provider catalog check, or `pnpm 0g:providers -- qwen3.7-flash 0gm-1.0-35b-a3b` to compare models. This does not make a paid inference or check the API key's model permissions. An exit code of 1 means a requested model has no healthy verified provider or the catalog lookup failed. Provider health and latency are snapshots, not guarantees.

`ZG_PROVIDER_SORT=latency` (the default) asks 0G to rank eligible providers by recently observed latency, with its normal provider failover. `ZG_PROVIDER_SORT=price` prefers the lowest price. Neither creates a verified provider when none exists, and neither guarantees lower end-to-end latency for every request. Latency sorting can choose a more expensive provider. Set `ZG_MAX_PROMPT_USD_PER_MILLION` and `ZG_MAX_COMPLETION_USD_PER_MILLION` to restrict provider prices; overly restrictive limits can eliminate all providers. These per-token price limits do not replace per-agent total spend controls. The existing conservative token reservations remain in place; requests with unknown billing outcomes are not automatically retried.

Successful Router calls record `latencyMs` with provider, verification and billing metadata, without adding prompt text to the Router request journal. Hosted runtime audit records may separately include outputs. Compare distributions and error rates over representative workloads and a sustained period before making latency or uptime claims; a one-word check is not a trading benchmark.

The Qwen3.7 Flash route was tested with a single minimal standard-mode request: it returned `OK` with 17 tokens and reported $0.000001 in Router billing. This does not establish verified trading availability. At that time its catalog listed only a standard-mode provider; the production-style verified request returned `no_provider_for_trust_mode`. The catalog also listed a healthy private-mode provider for `0gm-1.0-35b-a3b`, but the current API key returned `model_not_allowed` when tested. Provider availability and permissions can change; recheck rather than relying on the snapshot.

The 0G key's allowed models were subsequently expanded to include 0GM while retaining its existing $0.01 cap. With `ZG_0GM_DISABLE_THINKING=true`, an actual 0GM Router call returned `OK` in 2,022 ms and reported $0.000005. It requested verified routing, but its response did not include `tee_verified`; the harness correctly rejects it. Router selection of a verified provider is not independent cryptographic verification of the response. Do not change the guard to infer verification from a catalog entry or successful HTTP response. Resolve how to verify responses with 0G before enabling execution. The live key's $0.01 lifetime cap will eventually block more calls and is not a production operating budget.

`ZG_0GM_DISABLE_THINKING=true` opts into 0GM's documented `chat_template_kwargs.enable_thinking=false`; it is ignored for other models. 0G documents that thinking is on by default. Turning it off may change reasoning quality, so compare representative strategy and risk decisions before using it for anything beyond a smoke test. Neither short smoke-test latency nor an `OK` answer demonstrates acceptable trading accuracy. The sample configuration keeps thinking enabled by default.

To test the verified alternative, allow the model on the matching 0G Router API key in [the 0G dashboard](https://pc.0g.ai/), configure `ZG_MODEL_SMALL` and `ZG_MODEL_LARGE` only after choosing the model deliberately, and run `pnpm 0g:check`. This bounded check may incur inference charges. A healthy catalog entry does not prove the key can use the model, nor that the returned response will include the verification evidence required by the harness. The check fails if the response lacks the Router's verification flag.

0G's [provider routing documentation](https://docs.0g.ai/developer-hub/building-on-0g/compute-network/router/routing) describes trust modes, sorting, fallback, and price ceilings. Router and direct-provider accounts are separate; depositing funds into one does not automatically fund the other.
