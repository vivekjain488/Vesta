# RPC health observations

The monitor loads the completed RPC snapshot directly from Arkiv, verifies its row count and payload hashes, and samples public HTTPS URLs eligible under the resolver's URL and DNS policy. It sends one `eth_chainId` request and records whether the chain ID is correct, response time, HTTP status and selected rate-limit headers. It never calls transactions, load-tests endpoints, follows redirects, or sends private credentials. It is an independent host observation, not provider-provided uptime or an SLA.

Run `pnpm registry:health` in a terminal, or on macOS use `pnpm registry:health-service install`, `status`, and `stop`. The local launch agent runs while the Mac is awake and logged in; it is not a hosted service. It refreshes the target list hourly, issues at most four simultaneous probes every five seconds, leaves at least 60 seconds between calls to a hostname, honors `Retry-After` up to one hour on 429, and aims for at most one sample per endpoint per hour. Coverage takes time, especially when many endpoints share a host. Providers may see these probes from this machine's IP.

Results are stored on this host in `.perpetua/rpc-health.json` and, when `ARKIV_HEALTH_PRIVATE_KEY` or `ARKIV_MARKET_PRIVATE_KEY` is set, as `perpetua.rpc-health.v1` entities kept for 30 days. `GET /registry/health/<chainId>` merges that Arkiv history with the local file. The local file still fills gaps if Arkiv is briefly unavailable. Deploy the monitor and API on an always-on host so the history keeps growing. The UI shows each endpoint's latest result, HTTP status, latency, sampled success percentage over 24 hours and two per-endpoint graphs. Graphs use background history plus the latest on-demand result, deduplicated by sample timestamp; missing periods are not treated as failures. Latency includes DNS and connection setup from this one location. Availability is successes divided by actual probes, not an estimate of uninterrupted uptime; one successful probe yields 100% for one sample, not a 100% SLA. Stale data is labelled.

HTTP-only, WebSocket, credential templates, private URLs and non-standard ports are not probed and their table row explains why. A failed or missing probe does not remove an RPC from the source registry. Probes do not prove endpoint trustworthiness or permanent availability. Provider limits vary by IP, method, plan and time; an hourly maximum cannot be inferred from a successful low-volume probe. The UI does not show a guessed quota. The monitor still respects observed 429 and Retry-After signals. See [Geth JSON-RPC](https://geth.ethereum.org/docs/interacting-with-geth/rpc) and [an example provider's per-IP, per-method limits](https://nodely.io/docs/ethereum).

## Immediate checks

Opening a chain automatically checks eligible displayed endpoints whose background samples are missing or stale, in bounded batches. Select up to ten endpoint checkboxes and choose **Check selected** to check several independently. Results appear in the endpoint’s table row and graphs. The public `POST /registry/check/<chainId>` accepts `{ "snapshot": "<snapshot ID>", "hashes": ["<endpoint hash>"] }`; the server fetches and verifies those records from Arkiv before making any outbound request. It does not accept caller-supplied URLs or credentials. Endpoint results may be reused for 60 seconds, are kept in API memory, and do not modify the background monitor's 24-hour history. Concurrency, request rate, per-host pacing and 429 cooldowns are bounded; a capacity or cooldown message asks the user to retry. Key templates are labelled rather than tested; WebSocket and plain HTTP URLs cannot be checked by this HTTPS-only monitor. HTTP 401 means authentication is required, while 403 means access was denied; neither is evidence of a particular provider's key policy.

## Live graphs

While a chain's page is visible, the browser checks its displayed eligible HTTPS endpoints in groups of at most ten, with the next cycle scheduled 65 seconds after the previous cycle finishes. Larger chains, rate limits, slow endpoints and network errors can make updates take longer. The existing server-side concurrency, cooldown and 60-second result cache apply. Hidden tabs stop starting checks and refresh on return. The graphs default to a moving 30-minute window; a 24-hour view is available. The availability line is the rolling one-hour fraction of successful observed checks at each actual probe time, not continuous uptime. Latency plots only successful probes. Missing intervals remain gaps. On-demand samples stay in the open page and are also queued for Arkiv, so a reload can restore them from `GET /registry/health/<chainId>`. Opening one endpoint runs a deeper read-only inspection (block number, head age, archive and batch checks, client version, TLS) and stores that readout as a `perpetua.rpc-health.inspect.v1` entity.
